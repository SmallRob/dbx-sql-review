# v0.2.0 设计：批量数据库架构评审（Batch Schema Architecture Review）

> 状态：设计稿（待评审） · 目标版本：0.2.0 · 依赖：v0.1.33 已发布能力
> 一句话：在批量评审中，把用户上传的 SQL 脚本/文件夹还原成一份**跨文件的虚拟数据字典**，
> 在其上做表、索引、类型、关系的**架构级评审**，输出问题清单与可执行优化建议。

---

## 1. 背景与问题

当前批量评审（`batch.go`）是两层结构：

| 层 | 现有能力 | 缺口 |
|---|---|---|
| 文件级 | `AnalyzeSQL` 逐文件词法评审（SQL001–SQL087） | 只看单文件，看不到"用户表与订单表的 user_id 类型不一致" |
| 目录级 | SQL050/051/052 版本号重复/缺口/校验和重复 | 只校验文件元数据，不校验**数据库设计本身** |

用户诉求："上传 SQL 脚本或 SQL 文件夹 → 评审数据库表、索引等设计问题 → 给评审和优化建议"。
这不是现有规则的简单叠加，而是需要第三层：**Schema 级（跨文件）评审**。

### 1.1 边界声明（重要）

本功能坚持插件的根本安全边界：

- **不连接数据库、不执行被评审 SQL、不发起网络请求**；
- 评审对象是用户上传的 DDL/DML 脚本文本，构建的是"虚拟数据字典"；
- 真实库的表行数/统计信息无法获得，因此涉及"大表"的判定只给**提示级**建议，不冒充事实。

如需连真实库做 schema drift 比对，那是内部插件 `dbx-asdm-sqlreview` 的场景，不在本版本范围（见 §10 未来演进）。

### 1.2 目标 / 非目标

**目标**
1. 批量上传 SQL 脚本或文件夹后，自动构建虚拟数据字典（表/列/主键/索引/外键/字符集）。
2. 提供架构级规则集（表设计、索引设计、类型一致性、命名规范、关系完整性），输出问题与建议。
3. 评审结果中给出**可执行的优化建议**（正反 DDL 片段），并联动已有最佳实践库。
4. 结果可筛选、可下钻到源文件行、可导出 Markdown；AI 可通过 MCP 调用。

**非目标**
- 不自动改写用户的 SQL（`changed=false` 原则延续）。
- 不判定真实数据量、不生成 EXPLAIN、不连库。
- 不做 SQL 格式化/美化。

## 2. 核心概念：虚拟数据字典（VDD, Virtual Data Dictionary）

`SchemaModel` 是把整个批次的 DDL 汇总成的一份逻辑模型，是架构评审的**唯一事实源**。

```go
// backend/schema_model.go
type SchemaModel struct {
    Dialect     Dialect               `json:"dialect"`
    Tables      map[string]*TableDef  `json:"tables"`      // key: 规范化表名
    Indexes     []IndexDef            `json:"indexes"`
    Refs        []Reference           `json:"refs"`
    ObjectSrc   []ObjectSource        `json:"objectSrc"`   // 对象 → 源文件:行
    ParseErrors []ParseNote           `json:"parseErrors,omitempty"`
}

type TableDef struct {
    Name, QualifiedName string
    Columns      []ColumnDef
    PrimaryKey   []string
    Charset, Collation, Engine, Comment string
    Partitioned  bool
    SourceFile   string
    Line         int
}

type ColumnDef struct {
    Name, Type, RawType string
    Nullable, AutoIncrement bool
    Default, Comment string
    Length, Precision, Scale int
}

type IndexDef struct {
    Name, Table string
    Columns []string
    Unique  bool
    Kind    string // BTREE / HASH / GIN / FULLTEXT / ...
    SourceFile string
    Line int
}

type Reference struct {
    FromTable, FromColumns string
    ToTable,   ToColumns   string
    Kind string // FK / IMPLICIT(xxx_id 命名推断)
    SourceFile string
    Line int
}

type SchemaFinding struct {
    RuleID, Severity, Category, Title string
    Message, Advice string
    Tables []string
    Files  []string
    Evidence map[string]any
    PracticeIDs []string // 关联 practices.go 条目
}
```

### 2.1 构建流程

1. 复用 `lex.go` 的 tokenizer（4 方言已适配），新增轻量 DDL 提取器 `backend/schema_lex.go`；
2. 逐文件扫描语句：`CREATE TABLE` / `ALTER TABLE ...` / `CREATE INDEX` / `CREATE UNIQUE INDEX` / `COMMENT ON` / `FOREIGN KEY`；
3. 表名规范化：`db.t`、`[dbo].[t]`、`"schema"."t"`、反引号 `` `t` `` 统一为小写 `t`（保留 `QualifiedName` 原文）；
4. `ALTER TABLE` 合并到已有 `TableDef`（含 ALTER 顺序），得到最终状态；
5. 收集 DML/SELECT 的 WHERE/JOIN/ORDER BY 列，形成 `PredicateUsage`，用于"缺失索引"建议（§3 ARCH023）。

> 为什么不复用 `AnalyzeSQL` 的 `stmtInfo`：那是为了判定规则而 tokenize 的临时结构，未持久化；
> 直接改 `analyze.go` 会把它和规则判定强耦合。独立 `schema_lex.go` 风险更低、可单独测试。

## 3. 架构规则目录（ARCH 规则集）

新命名空间 `ARCH001–ARCH032`，与现有 `SQL0xx` 完全隔离，避免误伤既有规则与配置。

### 3.1 表设计（T）

| ID | 规则 | 严重度 | 说明 |
|---|---|---|---|
| ARCH001 | 表缺少主键 | high | VDD 层汇总判定（单表多文件 ALTER 后仍无 PK） |
| ARCH002 | 主键非整型/非递增 | medium | 方言差异：MySQL 有序 BIGINT、PG IDENTITY、SQLite rowid、SQL Server 窄聚簇键 |
| ARCH003 | 跨表主键类型不一致 | medium | `user_id` 在 A 表 BIGINT、B 表 VARCHAR |
| ARCH004 | 表/列缺少 COMMENT | info | 可由项目约定开关 |
| ARCH005 | 字符集/排序规则不统一 | medium | MySQL utf8mb4、SQL Server 排序规则一致性 |
| ARCH006 | 引擎未声明 / 混用 | medium | MySQL InnoDB；混用 MyISAM + InnoDB |
| ARCH007 | 宽表（列数超阈值，默认 50） | low | 新阈值 `wideTableColumns` |
| ARCH008 | 表名不符合 snake_case / 大小写混用 | low | 可约定关闭 |
| ARCH009 | 标识符过长 / 使用保留字 | medium | 按方言保留字表 |

### 3.2 列与类型（C）

| ID | 规则 | 严重度 | 说明 |
|---|---|---|---|
| ARCH010 | 同名逻辑列跨表类型不一致 | high | 最典型的架构隐患（外键列类型不匹配导致隐式转换） |
| ARCH011 | 金额使用浮点类型 | high | 联动 BP-GEN-012 |
| ARCH012 | 大字段/TEXT 出现在高频查询列 | low | 静态提示 |
| ARCH013 | 可空列无默认值 | info | 联动 BP-GEN-015 |
| ARCH014 | PG 时间类型未统一 TIMESTAMPTZ | low | 联动 BP-PG-006 |
| ARCH015 | PG 使用 JSON 而非 JSONB | medium | 联动 BP-PG-005 |

### 3.3 索引设计（I）

| ID | 规则 | 严重度 | 说明 |
|---|---|---|---|
| ARCH016 | 索引名在库内重复 | high | 跨文件才能发现 |
| ARCH017 | 冗余索引（前缀重叠） | medium | `(a)` 与 `(a,b)` 并存 |
| ARCH018 | 单列低区分度索引 | low | 按类型/命名启发式（status/type/gender） |
| ARCH019 | 单表索引过多（>6） | medium | 联动 BP-MY-003 |
| ARCH020 | 外键/引用列无索引 | high | 联动索引缺失 |
| ARCH021 | 表达式索引的列被函数包裹 | medium | 方言化（MySQL 8 函数索引 / PG 表达式索引） |
| ARCH022 | 复合索引顺序可疑 | low | 范围列在等值列之前的启发式提示 |
| ARCH023 | **谓词覆盖缺口** | medium | 汇总所有 WHERE/JOIN 列，指出高频过滤列无索引 —— 跨文件才可实现的核心价值 |
| ARCH024 | 索引命名不符合 `idx_<table>_<cols>` | info | 可约定关闭 |

### 3.4 关系完整性（R）

| ID | 规则 | 严重度 | 说明 |
|---|---|---|---|
| ARCH025 | 外键目标表不在批次内 | medium | 可能漏传脚本 |
| ARCH026 | 隐式引用（`xxx_id`）无 FK 也无索引 | low | 启发式，提示级 |
| ARCH027 | 循环外键 | high | 图检测 |
| ARCH028 | 外键 ON DELETE CASCADE 风险 | medium | 需显式确认 |

### 3.5 迁移与演进安全（M）

| ID | 规则 | 严重度 | 说明 |
|---|---|---|---|
| ARCH029 | 新增 NOT NULL 列无默认值 | high | 现有数据无法填充 |
| ARCH030 | 建索引未用在线方式（汇总） | medium | 把散落的 SQL021 聚合成"本次变更共 N 处在线索引风险" |
| ARCH031 | 单文件跨多表结构变更 | low | 回滚粒度提示 |
| ARCH032 | 表/索引重复定义 | high | 两个文件都 CREATE 同名表且无 IF NOT EXISTS |

> 规则可通过 `config.rules.disabled` / `severity` 单独关闭或降级，与现有规则共用同一套配置机制。

## 4. 优化建议生成

每条 `SchemaFinding` 关联 `practiceIds`（来自 `practices.go` 的 schema/index/transaction/architecture 分类，约 30 条可复用条目）。

建议生成原则：

1. **只给可执行片段**：正反 DDL 示例（`goodSql`/`badSql`），沿用 Practice 数据结构；
2. **按表聚合**：同一张表的问题合并成一条"表级优化建议卡"，避免碎片化；
3. **不自动改写**：延续 `changed=false`，不给"一键修复"；
4. **标明依据**：显示命中的 ARCH 规则 + 关联最佳实践 ID + 源文件位置。

示例输出：

```
[ARCH010 high] user_id 类型不一致
   orders.user_id  BIGINT       (V2.1.3__orders.sql:12)
   audit.user_id   VARCHAR(64)  (V2.2.8__audit.sql:7)
  建议：统一为 BIGINT，避免 JOIN 隐式转换导致索引失效。
  关联：BP-GEN-001 最左前缀 / BP-MY-036 可变长主键
```

## 5. 评分与分级

**决策：v0.2.0 架构评审使用独立评分，不改动现有六维质量分**（保证向后兼容，避免历史报告等级漂移）。

```go
type ArchitectureReport struct {
    Score       int              `json:"score"`        // 0-100，同规则递减计分（v0.1.32 算法）
    Grade       string           `json:"grade"`
    GradeLabel  string           `json:"gradeLabel"`
    Findings    []SchemaFinding  `json:"findings"`
    Tables      []TableDef       `json:"tables"`
    Indexes     []IndexDef       `json:"indexes"`
    Suggestions []SchemaSuggest  `json:"suggestions"`
    Stats       ArchitectureStats `json:"stats"`
}
```

- 复用 v0.1.32 的**同规则递减计分**（首次全额、其后 25%、单规则封顶 2×），避免同类问题刷爆分数；
- 等级映射沿用 `A+/A/B/C/D/E`；
- 六维 `QualityMetrics.Dimensions` 保持不变；架构分在 UI 单独展示。
- v0.3.0 可在完成基线对比后，把"架构设计"作为第 7 维并入整体质量分（见 §10）。

## 7. UI 设计（炫彩渐变风格）

批量页 `#tab-batch` 的报告区升级为分区结构：

```
┌─ 批量报告 ────────────────────────────────────────────┐
│ [质量评分环]  文件 N · 语句 N · 等级分布 pills        │
├────────────────────────────────────────────────────────┤
│ 子标签：架构评审 | 文件明细 | 目录一致性               │
├────────────────────────────────────────────────────────┤
│ 架构评审：                                            │
│  ┌ 架构分环(渐变) ┐  统计 chips: 表 12 / 索引 34 /     │
│  │    78 / B      │  列 156 / 外键 8 / 问题 23         │
│  └───────────────┘  严重度筛选 pills                  │
│  问题卡片（按表分组）：                                │
│   ▸ [ARCH010 high] user_id 类型不一致   orders, audit │
│     · 展开：证据表 + 源文件:行 + 关联最佳实践          │
│     · [跳转文件] 按钮                                 │
│  优化建议卡：按表聚合，正反 DDL 代码块，复制按钮       │
│  表结构矩阵：表名 | 列数 | 主键 | 索引数 | 字符集 | 问题数 │
└────────────────────────────────────────────────────────┘
```

实现要点：
- 新增 CSS 变量 `--grad-1/--grad-2` 用于评分环与建议卡渐变；沿用暗色主题；
- 复用 `renderQualityCard` 的 SVG 环组件，参数化颜色与标题；
- 问题卡沿用 `.finding` 样式，`<details>` 折叠展开（避免 v0.1.33 的遮挡问题）；
- 架构分环与建议区都是 `flex:0 0 auto`，只有列表区滚动；
- 补上进度条：监听 `batch/progress` 事件，架构分析阶段单独显示进度；
- 文件明细表补"架构问题数"列，点击跳转到架构评审对应分组。

## 8. 性能与规模

| 项 | 要求 |
|---|---|
| 文件上限 | 沿用 800（`MaxFilesPerBatch`） |
| 解析 | 单次线性扫描，VDD 构建 O(语句数) |
| 规则评估 | 用 map 索引（按表名/列名/索引名），避免 O(n²)；关系图用邻接表 |
| 建议上限 | 每规则最多 50 条 finding，超出聚合为"另有 N 条" |
| 进度 | 解析/建模型/规则评估/建议生成 4 阶段上报进度 |
| 超时 | UI `batch/run` 保持 600s；架构报告单独可重取 |

## 9. 兼容性与风险

| 风险 | 缓解 |
|---|---|
| DDL 方言差异大 | 4 方言的 tokenizer 已存在；ARCH 规则内做方言分支；测试覆盖 4 方言样例 |
| 跨表同名列类型不一致可能是业务故意 | 默认 medium/info，可按规则关闭；文案强调"确认是否故意" |
| 谓词覆盖缺口（ARCH023）误报 | 只把**出现在 WHERE/JOIN 且无索引**的列列为 medium 提示；动态 SQL 列跳过 |
| 解析失败（复杂 DDL） | 记录 `ParseErrors`，不阻断评审；报告中显示"N 处语句未能解析" |
| 800 文件性能 | 见 §8；提供 `--skip-architecture` 配置回退到旧行为 |
| 旧报告格式 | 新增字段全部 additive；`batch/architecture` 按需重取 |

## 11. 验收标准

1. 上传 186 个 asdm 迁移脚本（现有基线），架构评审完成 < 30s，输出 VDD 与 findings；
2. 4 方言各有 ≥3 条可触发的 ARCH 规则的单元测试；
3. `batch/run` 返回 `report.architecture`，旧字段不变；`go test ./...` 全绿；
4. UI 架构评审区在 1280×720 与面板模式下无遮挡、可折叠、可下钻；
5. Markdown 导出含"架构评审"章节（统计 + 问题 + 建议）；
6. MCP `sql_schema_review` 可被 AI 调用并返回结构化建议；
7. 全程不连库、不执行 SQL、不发网络请求（安全边界回归测试）。
