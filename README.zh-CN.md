# SQL Review for DBX

静态 SQL 评审工作台：把一段 SQL 或整个迁移目录交给确定性规则引擎，
产出**逐条命中**（行号、片段、建议）与**质量画像**。

**不连接数据库，不执行被评审的 SQL。**

[English](README.md) · 中文

## 它解决什么

写 SQL 和评审 SQL 的人之间通常隔着一道人工工序：评审者要凭经验读一遍脚本，
指出「这里会锁表」「这里全表扫」「这里重放会报错」。这套工序的问题是：

- **不可复现**——换个评审者结论就变了；
- **发现得太晚**——问题往往在测试环境跑挂之后才被看见；
- **不覆盖全量**——人工不可能每次都读完 181 个迁移脚本。

本插件把这套工序变成一组可开关的规则：同样的输入永远得到同样的结论，
目录级的批量评审让人不必逐个读脚本。

## 核心保证

| 保证 | 怎么做到的 |
|---|---|
| 绝不连库 | 后端没有 `database/sql` 导入，没有数据库驱动，没有连接配置字段 |
| 绝不执行 SQL | 只做词法分析（tokenize + 规则匹配），没有执行语句的代码路径 |
| 无网络访问 | sidecar 不发起任何网络请求，不需要任何 host 权限 |
| 不碰凭据 | 不保存 host/账号/口令——配置里只有规则开关与阈值 |
| 构建可复现 | SDK 随仓库自带，`GOPROXY=off` 也能编译出同样的二进制 |

## 规则集（64 条）

| 类别 | 条数 | 代表规则 |
|---|--:|---|
| 破坏性 | 12 | `SQL001` 删表/删库 · `SQL003` UPDATE/DELETE 无 WHERE · `SQL073` 动态 EXEC · `SQL087` CASCADE |
| 迁移规范 | 17 | `SQL010` 文件命名不规范 · `SQL014` 单文件语句过多 · `SQL070` SQL Server DDL 缺少守卫 · `SQL080` PostgreSQL DDL 缺少守卫 |
| 性能 | 15 | `SQL022` SELECT * · `SQL023` 无谓词全表扫描 · `SQL028` 深分页（大 OFFSET）· `SQL029` 超大 IN 列表 · `SQL039` 多表连接扇出 · `SQL071` NOLOCK · `SQL081` 索引未用 CONCURRENTLY |
| 结构质量 | 16 | `SQL030` 建表缺主键 · `SQL032` 浮点存金额 · `SQL075` 非 Unicode 类型 · `SQL084` SERIAL · `SQL085` JSON 未用 JSONB |
| 敏感数据 | 1 | `SQL040` 敏感列（password/token/身份证/手机/银行卡…） |
| 目录一致性 | 3 | `SQL050` 版本重复 · `SQL051` 版本缺口 · `SQL052` 不同版本内容雷同 |

### 项目约定类规则默认关闭

`SQL012`（DDL 幂等守卫）、`SQL018`（必须写 `USE`）、`SQL033`（列必须有 `COMMENT`）、
`SQL034`（必须显式 `ENGINE`）、`SQL070`（SQL Server DDL 幂等守卫）、
`SQL080`（PostgreSQL DDL 幂等守卫）——这些是**团队约定**，不是通用 SQL 质量问题。
通用插件不该拿自己的房规去衡量别人的仓库，所以它们默认关闭，
在「规则」页按你的规范勾选即可。

### 方言

支持 MySQL、SQLite、SQL Server/T-SQL 与 PostgreSQL，规则按方言自动分流。SQL Server 支持
`GO`、方括号标识符、临时表、`TOP`、`IDENTITY` 与命名约束（`SQL070`–`SQL077`）。
PostgreSQL 支持美元引号函数体、`::` 强转、`ON CONFLICT`、`RETURNING`、`JSONB`、
IDENTITY 与时区类型（`SQL080`–`SQL087`），覆盖 DDL 重放守卫、`CONCURRENTLY`、
改列类型重写、`SET NOT NULL`、`SERIAL`、`JSON`、无时区时间和 `CASCADE`。
四种方言均只做静态分析。

## 界面

五个页签：

- **评审**——从文件打开、粘贴或拖入单个 `.sql` 文件；顶部评分环给出质量分/等级/风险结论，六维健康度带命中数，命中列表可筛选、折叠证据、复制建议并定位 SQL 行；命中规则时结果底部联动展示**相关最佳实践**，附可复制的代码示例；
- **批量目录**——一次拖入多个脚本；已选文件列表显示行数与体积，支持去重、单条移除和清空；评审后展示整批评分环与等级分布，并可导出 Markdown；
- **规则**——按类别查看全部规则，逐条开关与调级别；
- **最佳实践**——62 条规则化的优化条目，按方言与分类（索引、查询、表结构、事务与锁、内存、配置、架构、诊断）组织；每条含原理、推荐做法、反例、正反 SQL 示例与关联规则 ID。支持按方言、分类与关键词筛选，可从评审建议一键跳转；
- **记录**——评审历史与哈希链校验。

### 最佳实践目录

内容整理自 ASDM《[MySQL 数据库性能优化最佳实践](https://asdm-platform.leansoftx.com/portal/practices/29)》，并按各引擎实现机制改写。16 条通用条目适用所有方言，引擎专属条目按方言路由（含通用项后：MySQL 34 条、PostgreSQL 26 条、SQL Server 26 条、SQLite 24 条）。它是一份纯静态知识库，通过 `ruleIds` 与评审规则交叉引用，不连库、不执行 SQL。单条评审时，`suggestedPractices` 依据命中规则填充并附到结果上。

## 内置 AI / MCP 工具

插件启用 `external_tools` 与 `ai_tools`，向 DBX 内置 Agent 和 MCP 客户端暴露
5 个只读工具：

- `sql_review`：评审 SQL，返回逐条发现、`reviewId` 及相关最佳实践（`result.suggestedPractices`）；
- `sql_review_result`：读取最近一次或指定评审，支持按严重级别、规则过滤与分页；
- `sql_optimize`：返回结构化优化动作，供 Agent 生成可复核补丁（`changed=false`，不做未经证明的自动改写）；
- `sql_rules`：列出规则目录，可按方言过滤；
- `sql_best_practices`：按方言/分类列出最佳实践，或传入 `sql` 只返回与该 SQL 命中相关的条目。

最近 32 次单条评审只缓存在 sidecar 内存中；结果读取不返回原始 SQL，原始 SQL
也不落盘。所有工具继续保持不连接数据库、不发起网络请求、不执行 SQL 的边界。

## 报告口径

除了逐条命中，还给一个**质量画像**：

- `quality`（质量分）= 100 − 风险分，越大越好，是给人看的结论；
- `score`（风险分）= Σ 罚分（critical 40 / high 20 / medium 8 / low 3 / info 0），用于排序；
- 六个维度各自算健康度（`100·e^(−维度罚分/55)`），用饱和曲线避免「20 条缺注释把维度压成 0」；
- 等级受**最重命中封顶**：出现 critical 一律 E，出现 high 最多 C——
  避免一堆提示把分数拉高，却掩盖了一条 `DROP TABLE`。

批量聚合按语句数加权平均，而不是把罚分相加：否则一个重灾文件会让整批归零，
掩盖其余文件都通过的事实。

## 已知边界

- **只是评审台，不是守门人。** DBX 没有执行前钩子，本插件不能阻止语句执行；
  它让问题在提交前浮现，而不是在执行时拦截。
- **词法级，不是语法树。** 动态拼接的标识符（`CONCAT('t_', @suffix)`）无法还原；
  这类语句会被标记为「动态」，只分析其中的字面量分支。PostgreSQL 美元引号中的
  `DO`/`CREATE FUNCTION` 函数体保持不透明：外层脚本会评审，但函数体内的
  PL/pgSQL 语句不做静态审计。
- **拿不到真实行数。** 因为不连库，无法判断某张表到底多大。
  `SQL020`/`SQL021` 因此对所有结构性 ALTER 提示，而不是「仅当大表才报」——
  这是刻意的取舍：宁可多提示一条，也不给一个基于猜测的结论。
- **审计链不是身份认证。** 记录以 append-only 哈希链保存，能证明记录未被事后改写，
  但**不能**证明是谁写的——评审人是自填标识，没有身份校验。
- **目录一致性只覆盖目录自身。** 真正的「库里有、本地没有」这类漂移，
  需要与目标库比对才能发现；本插件不连库，所以只报目录内部能看出来的问题
  （版本重复、版本缺口、内容雷同）。
